## 1. Что это

`aiCostTracker` (бинарник `aicost`) — CLI-инструмент на **Go**, который
собирает расходы и использование по нескольким AI-провайдерам (Anthropic,
OpenAI и далее) в **один локальный дашборд** в терминале.

Проблема, которую он решает: в 2026 активный AI-разработчик обычно платит
3–5 провайдерам одновременно (Claude/Anthropic ежедневно, плюс, как правило,
OpenAI и другие). Нет единого места, где видно **общий** расход — приходится
логиниться в 3–5 биллинг-консолей по отдельности. `aicost` тянет usage/cost
через официальные API провайдеров, нормализует их в общую модель и показывает
сводную таблицу «сколько потрачено за период по каждому провайдеру».

Это **не сервис** и **не SaaS**: чистый CLI-бинарник. Ни сервера, ни хостинга,
ни «звонков домой». Единственное локальное состояние — SQLite-файл с историей
снапшотов, чтобы строить тренды по времени, а не только «текущий баланс».

## 2. Зачем (и почему именно так)

Проект — **соло pet-проект интроверта с приоритетом обучения Go**. Реализация
ведётся AI-ассистентом по фиксированному пайплайну (см. `CLAUDE.md`). Это не
бизнес: экономическая целесообразность не требуется, метрика успеха — сам автор
им пользуется (dogfooding на собственных счетах провайдеров) и Go осваивается.

Учебная нагрузка на стандартную библиотеку: структура `cmd/`+`internal/`,
ручной `net/http`-клиент с retry/backoff к нескольким разным API,
нормализация разнородных ответов в общую модель, работа с SQLite,
table-driven и golden-тесты, кросс-компиляция.

Ключевые принципы:

- **Нулевая инфраструктура и ≈ $0/мес.** Чистый CLI, без сервера. Обращения к
  provider usage API — только по явной команде пользователя, не по расписанию.
- **BYOK, admin-ключи только локально.** Ключи читаются из конфига/окружения,
  никогда не попадают в git/логи/вывод. Отдельного логгера/`--verbose` в проекте
  пока нет (см. TECHNICAL_PLAN §2); если появится диагностический вывод, секреты
  не должны попадать в него даже на уровне debug.
- **Порт-адаптер `ProviderUsageSource`.** Каждый провайдер — отдельный адаптер за
  единым интерфейсом; добавить провайдера = добавить один файл, не трогая CLI,
  хранилище и рендер (те же ports & adapters, что в `gitl` и KnowledgeVault).
- **Локальная история для трендов.** SQLite-снапшоты, чтобы видеть динамику
  расхода во времени, а не только моментальный срез.
- **Без телеметрии.** Данные о расходах — приватны и наружу не уходят.

## 3. Для кого

- **Прежде всего — сам автор:** один взгляд в терминал вместо обхода 3–5 консолей.
- Соло-разработчики и мелкие команды с несколькими AI-подписками, которым нужен
  агрегированный обзор расходов без построения собственного сервиса.

## 4. Ключевой технический вызов: у провайдеров разные usage-API

Главная сложность проекта (и то, ради чего заведён порт-адаптер):

- У каждого провайдера **свой** API для usage/billing-данных, со своей
  авторизацией, пагинацией и формой ответа.
- Usage/cost-эндпоинты обычно требуют **отдельного admin/org-level ключа**,
  отличного от обычного ключа для вызова моделей. Это влияет на схему конфига:
  для каждого провайдера храним именно admin-ключ, и в UX явно объясняем, где
  его взять.
- Точные эндпоинты и форматы на момент планирования **не зафиксированы как факт**
  — они помечены `[ASSUMPTION]` в `TECHNICAL_PLAN.md §4` и подлежат проверке по
  живой документации в **Этапе 1**. Мы не выдумываем несуществующие эндпоинты.

Ответ на вызов — интерфейс `ProviderUsageSource` (см. `TECHNICAL_PLAN.md §3`):
адаптер сам знает, как сходить в свой API и авторизоваться, и отдаёт наружу
уже нормализованный `Snapshot`. Различия провайдеров не протекают в остальной код.

## 5. MVP — две фазы

**Фаза 1 (Этапы 0–4): базовый агрегатор.**

- Минимум **2 провайдера** — Anthropic + OpenAI — через их usage/cost API.
- Команда `report`: «сколько потрачено за период по каждому провайдеру» —
  CLI-таблица.
- Локальное хранение снапшотов в SQLite (`history`-команда покажет их позже).

**Фаза 2 (post-MVP):** больше провайдеров, тренды и алерты — см.
[`POST_MVP_PLAN.md`](./POST_MVP_PLAN.md). Статус на момент правки: OpenRouter,
тренды/графики (`--chart`/`--by-model`/`--compare`), алерты по порогу расхода,
`--format=json` и точность денежных сумм (`int64` микро-USD) — реализованы;
Google Gemini отложён (нет REST-API истории расходов под admin-ключ), TUI
(bubbletea) — кандидат.

## 6. Что сознательно НЕ входит в MVP

- Веб-интерфейс, сервер, «облако» — принципиально нет.
- Realtime-мониторинг / фоновый демон — обращения только по команде.
- Прогноз расхода, бюджеты по проектам, мультивалютность — кандидаты post-MVP.
- Публичный Go-API (`pkg/`) — появится только при реальном спросе.
